03

根本原因

レスポンスヘッダーに原因がそのまま出ています。実際に取得した値です。

server: cloudflare
cf-edge-cache: cache,platform=wordpress
vary: User-Agent            ← エッジキャッシュを事実上無効化
cf-cache-status: DYNAMIC    ← HTML がキャッシュされていない
cf-ray: a39371aeef9cc36d-PDX   ← 米国オレゴンのエッジに着弾

cf-cache-status: DYNAMIC は、Cloudflare のエッジに到達したリクエストが毎回そのまま日本のオリジンサーバーまで転送されていることを意味します。米国からだと太平洋を往復するため、これだけで数百ミリ秒が確定で乗ります。

さらに vary: User-Agent が付いているため、仮にキャッシュを有効化しても User-Agent 文字列ごとに別エントリとして保存され、ヒット率はほぼゼロになります。この2つを直すことが最優先です。

04

改善策（効果の大きい順）

1〜4 が Phase 1、5〜9 が Phase 2
1

Cloudflare で HTML をエッジキャッシュする

−0.5〜0.8秒

設定のみ最も効果が大きく、コード変更が不要な施策です。

  • Cloudflare APO for WordPress（月額5ドル）を有効化する。WordPress 向けに HTML を全世界のエッジに配信する専用機能で、まさにこの問題のための仕組みです。cf-edge-cache ヘッダーが出ているので Cloudflare の WP プラグインは既に入っており、APO を有効にするだけの可能性が高いです。
  • APO を使わない場合は、Cache Rule で「Cache Eligibility: Eligible for cache」＋ Edge TTL を設定し、wp-admin とログインクッキー保持時はバイパスする。
  • vary: User-Agent を外す。これが残っているとキャッシュはほぼ効きません。モバイル判定プラグインかテーマの設定が出力元です。

想定効果：TTFB 570–900ms → 30–80ms。全ページ・全ユーザーに効きます。

2

PNG バナー4枚を WebP / AVIF に変換する

−1.6〜2.1MB

設定のみ写真がPNGで保存されています。PNG は透過やフラットな図版用で、写真には不向きです。

633KB  DAIKOKU-TOUR バナー-1024x576.png
560KB  JDM-TOUR バナー-3-1024x576.png
545KB  image-1-1024x576.png
537KB  image-1024x576.png
─────
2,275KB → WebP なら合計 250KB 程度
  • 既に EWWW Image Optimizer が入っているので、WebP 変換と配信（Easy IO もしくは WebP リライト）を有効にする。
  • または Cloudflare Polish + WebP（Pro プラン）を使えば、画像を差し替えずに自動変換されます。

モバイルの体感に最も効きます。低速回線ではこの2MBが数秒の差になります。

3

メインビジュアルを最優先で読み込ませる

−0.3〜0.9秒

テーマ編集LCP（最大要素の描画）の対象は、トップのスライダー画像 メインビジュアル用.jpeg です。モバイルの初回計測では 3,400ms かかっていました。

div.p-mainVisual__inner > div.p-mainVisual__slide
  > picture.p-mainVisual__imgLayer > img.p-mainVisual__img
  • この <img> に fetchpriority="high" を付ける。
  • 遅延読み込みの対象から外す。ファーストビューの画像を lazy-load すると LCP は必ず悪化します。
  • <head> に <link rel="preload" as="image" imagesrcset="…"> を追加する。
  • lazysizes が EWWW と SWELL の2本読み込まれています。どちらか一方で十分です。
4

Cloudflare Rocket Loader を無効にする

TTI 改善

設定のみ全スクリプトが type="b5740862f4b864a7b2f4bfff-text/javascript" に書き換えられており、Rocket Loader が有効になっています。

Rocket Loader は JS の実行を後ろへずらす機能ですが、このサイトでは TBT が既に 0.00〜0.08秒で、遅延させるべき負荷が存在しません。一方でメインビジュアルのスライダー制御（set_mv.min.js）まで遅延させるため、LCP と TTI 6.57秒 を悪化させている可能性が高いです。オフにして再計測してください。

5

Google タグの重複を解消する

−173KB

タグ設定GTM と gtag が両方読み込まれています。

173KB  googletagmanager.com/gtag/js?id=GT-TX9NK383
115KB  googletagmanager.com/gtm.js?id=GTM-WFGD8X5Q

計測基盤が二重です。GTM に一本化し、GA4 は GTM 内のタグとして設定すれば、173KB とメインスレッド処理が丸ごと減ります。サードパーティ JS はモバイルでメインスレッドを 370ms 占有しています。

6

静的ファイルのキャッシュ期間を延ばす

再訪問が高速化

設定のみ24〜26個のファイルでキャッシュ期間が短すぎると指摘されています。/wp-content/* に対して Cache-Control: public, max-age=31536000, immutable を設定してください。SWELL のアセットは ?ver=2.12.0 でバージョン管理されているため、長期キャッシュしても更新時に問題は起きません。

7

Trustindex を遅延読み込みにする

−24KB + 実行時間

軽微口コミウィジェット cdn.trustindex.io/loader.js はページ下部にあるため、初期表示には不要です。スクロールで表示領域に入ってから読み込むようにしてください。

8

Web フォントに font-display: swap を指定する

体感改善

軽微アイコンフォント icomoon.woff2 の読み込み中にテキストが不可視になっています。font-display: swap を指定すれば、フォント取得前でも本文が表示されます。

9

未使用の CSS / JS を削減する

−40KB / −164KB

要検証SWELL の blocks.css(23KB) と main.css(22KB) が全ページで読み込まれています。SWELL の「CSSを直接読み込む／インライン化」設定やページ単位の出し分けで削減できますが、1〜4 を先に実施した後の効果測定を見てから着手してください。上位施策だけで目標に届く可能性が高いためです。

06

計測について

この診断は GitHub Actions の米国リージョンのランナーから Lighthouse 12 を実行し、モバイル・デスクトップ各3回の中央値を取ったものです。計測一式はリポジトリにコミット済みで、Actions → Performance audit (US) からいつでも再実行できます。毎週月曜にも自動実行されるため、改善の効果をそのまま数値で追えます。

注意点：TTFB は実行ごとに 570〜900ms とばらつきがあります。これはエッジキャッシュが無く、オリジンの状態に左右されるためで、ばらつき自体が施策1の必要性を裏付けています。また Lighthouse はラボ計測であり、実ユーザーの体感とは異なります。改善後は Google Search Console の Core Web Vitals（実ユーザーデータ）も併せて確認することをおすすめします。
