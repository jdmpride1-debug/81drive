02

用語のミニ解説

この4つだけ覚えれば読めます
LCP
ページで一番大きい画像や見出しが表示されるまでの時間。訪問者が「表示された」と感じる瞬間。今の最重要指標です。
TTFB
サーバーが最初の1文字を返すまでの時間。ここは 0.02秒 まで改善済みで、もう問題ありません。
KB / MB
訪問者がダウンロードするデータ量。1,000KB = 1MB。少ないほど速く、スマホの通信量も減ります。
キャッシュ
一度作ったページをコピーして近くに置いておく仕組み。Cloudflare が米国内にコピーを置いてくれています。
03

やること（この順番で）

上から順に、効果の大きい順
STEP 1

Googleタグを1本にまとめる

−1.67秒コード編集なし
なぜ必要か：今、同じアクセス解析のプログラムが3本も読み込まれています。合計 459KB で、これはページ内のJavaScript 522KB のほとんどを占めています。3本あっても計測結果が3倍正確になるわけではなく、単純に無駄です。Lighthouse はこれを直すだけで 1.67秒 速くなると試算しています。 
172KB  gtag/js?id=GT-TX9NK383            ← どこかに直接貼られている
172KB  gtag/js?id=GT-TX9NK383&cx=c...   ← GTM が読み込んでいる
115KB  gtm.js?id=GTM-WFGD8X5Q            ← GTM 本体
─────
459KB  すべて同じ GT-TX9NK383 を計測している

まず「どこに貼られているか」を探します。

  1. Chrome で https://81drive.com/ を開きます。
  2. ページ上で右クリック→「ページのソースを表示」を選びます。英数字がびっしり並んだ画面が出ますが、読む必要はありません。
  3. Ctrl + F（Macは ⌘ + F）を押して、検索欄に GT-TX9NK383 と入力します。
  4. 検索欄の横にヒット件数が出ます。これが 2件以上なら、GTM とは別に直接貼られたタグがあります。

次に、その直接貼られたタグを消します。心当たりのある場所を上から順に確認してください。

  1. SWELLの設定を見る — WordPress管理画面の SWELL設定 → 一般 を開き、「Google Analytics」「Googleタグ」「head内に出力するコード」といった入力欄に GT-TX9NK383 や gtag が入っていないか確認します。入っていたらその欄だけを空にして保存します。
  2. プラグインを見る — プラグイン → インストール済みプラグイン で、「Site Kit by Google」「GA Google Analytics」など解析系プラグインが有効になっていないか確認します。GTMを使うなら、これらのAnalytics連携をオフにします。
  3. カスタマイザーを見る — 外観 → カスタマイズ → 高度な設定（またはCSS/HTML追加欄）に貼られていないか確認します。
  4. 消したら保存し、Cloudflare のキャッシュを消します（STEP 5 の手順）。その後、上の検索をもう一度行ってヒット件数が減ったか確認します。
判断に迷ったら
GTM（タグマネージャー）を広告タグなどにも使っていますか？
・使っている → GTM を残し、直接貼られた gtag を消す。（−172KB）
・使っていない／わからない → GTM のほうを外し、gtag だけ残すのが最軽量です。（−287KB）
どちらにしても計測は止まりません。作業後に Google アナリティクスの「リアルタイム」で自分のアクセスが表示されるか確認してください。
できたらこうなる
ソースを検索したときの GT-TX9NK383 のヒットが減り、次回の計測で JavaScript が 522KB → 250〜350KB に下がります。
STEP 2

画像をWebP形式に変換する

−2.0MBコード編集なし
なぜ必要か：バナー4枚が PNG形式のまま置かれています。PNG はイラストや透過画像用の形式で、写真には向いていません。WebP という新しい形式に変えると、見た目はほぼ同じまま容量が10分の1程度になります。今この4枚だけで 2.2MB あり、ページ全体の8割を占めています。 
633KB  DAIKOKU-TOUR バナー-1024x576.png
560KB  JDM-TOUR バナー-3-1024x576.png
545KB  image-1-1024x576.png
537KB  image-1024x576.png
─────
2,275KB  → WebP なら合計 250KB 程度

すでに EWWW Image Optimizer というプラグインが入っているので、設定を変えるだけで実行できます。

  1. WordPress管理画面の 設定 → EWWW Image Optimizer を開きます。
  2. WebP変換をオンにします。「Easy Mode」画面なら 「WebP変換」のスイッチをオン。「Advanced（詳細）」画面なら WebPタブの「JPG/PNG から WebP」にチェックを入れます。
  3. 配信方法を選びます。同じWebP設定欄の中に配信方法の選択があります。このサイトは Cloudflare 経由なので 「JS WebP Rewriting」または「<picture> WebP Rewriting」を選んでください。（.htaccess方式はCloudflareと相性が悪く、うまく届かないことがあります）
  4. 変更を保存します。
  5. 既存の画像を一括変換します。メディア → 一括最適化 を開き、「最適化されていない画像をスキャンする」→ 見つかったら 「最適化を開始」を押します。画像の枚数によっては数分かかります。画面を閉じずに終わるまで待ってください。
  6. 終わったら Cloudflare のキャッシュを消します（STEP 5 の手順）。
念のため
一括最適化は元画像を置き換える処理です。作業前にバックアップを取っておくと安心です。EWWW には元画像を保管する設定（Backup originals）もあるので、オンにしておくと元に戻せます。
できたらこうなる
次回の計測で、デスクトップのページ容量が 2,995KB → 800KB前後に下がります。スマホの通信量も大きく減ります。
STEP 3

トップの大きな画像を「最優先」で読み込ませる

表示の安定化設定で対応可
なぜ必要か：トップページの一番大きい画像（メインビジュアル）が、「後回しでいい画像」として扱われています。そのため読み込みが遅れ、計測3回のうち1回は表示に 7.38秒 かかりました（他2回は2.5秒）。このばらつきがまさにその証拠です。「最初に見える画像は後回しにしない」と指定すれば安定します。

EWWW の遅延読み込み機能から、この画像だけを除外するのが一番安全な方法です。

  1. 設定 → EWWW Image Optimizer を開きます。
  2. 「Lazy Load」（遅延読み込み）の設定欄を探します。「Easy Mode」にある場合と、「Advanced」の中にある場合があります。
  3. その近くにある「除外するもの」「Exclude」という入力欄に、次の1行を貼り付けます。
    p-mainVisual__img
  4. 保存します。
  5. SWELL側にも遅延読み込み設定があります。SWELL設定 → 高速化 を開き、「遅延読み込み」の項目に除外設定があれば同じ文字列を追加してください。
補足
遅延読み込みのプログラム（lazysizes）が EWWW と SWELL で2本読み込まれています。どちらか片方で十分なので、SWELL設定 → 高速化 で遅延読み込みをオフにして EWWW 側に任せると、さらに軽くなります。ただし STEP 1・2 を終えてから、1つずつ試してください。
できたらこうなる
計測3回の LCP のばらつき（7.38s / 2.54s / 2.53s）が揃い、毎回ほぼ同じ数値になります。
STEP 4

外部サーバーへの接続を前倒しする（preconnect）

−0.33秒1行追加
なぜ必要か：Googleや口コミサービスなど外部のサーバーから読み込むファイルがあります。ブラウザは「必要だとわかった時点」で接続を始めるため、その分だけ待ち時間が生まれます。「あとでこのサーバーを使うよ」と先に伝えておくと、その待ち時間が消えます。Lighthouse の試算で 0.33秒 の短縮です。
  1. SWELL設定 → 一般 の中にある「<head>内に出力するコード」の入力欄を開きます。（STEP 1 で確認した欄と同じ場所です）
  2. 次の3行をそのまま貼り付けて保存します。
<link rel="preconnect" href="https://www.googletagmanager.com" crossorigin>
<link rel="preconnect" href="https://cdn.trustindex.io" crossorigin>
<link rel="preconnect" href="https://static.cloudflareinsights.com" crossorigin>
順番に注意
STEP 1 を先に終わらせてください。STEP 1 で GTM を外した場合、1行目は不要になります。
STEP 5

Cloudflareのキャッシュを消す（毎回の仕上げ）

30秒
なぜ必要か：Cloudflare は古いページのコピーを持っています。設定を変えてもコピーが残っていると変更が反映されません。「直したのに変わらない」の原因はほぼこれです。STEP 1〜4 のあと毎回実行してください。
  1. dash.cloudflare.com にログインします。
  2. サイト一覧から 81drive.com を選びます。
  3. 左メニューの 「Caching」→「Configuration」を開きます。
  4. 「Purge Everything」（すべて削除）ボタンを押し、確認ダイアログでもう一度押します。
  5. 1〜2分待ってから、スマホやシークレットウィンドウでサイトを開いて確認します。
ついでに直せること
現在キャッシュの有効期間が 4時間（max-age=14400）です。今回の計測はちょうど期限切れの瞬間に当たりました（cf-cache-status: MISS）。4時間ごとに1人目の訪問者だけが遅くなる状態なので、Caching → Configuration → Browser Cache TTL や Cache Rule の Edge TTL を1日以上に伸ばすと安定します。更新時は上の Purge を実行すれば即座に反映されます。
