この順番には理由があります
  1. 1回に1つだけ変える。2つ同時に変えると、数字が動いたときどちらが効いたのか分かりません。効かなかった変更を元に戻すこともできなくなります。
  2. 変更したら1時間空けてから計測する。更新直後はCloudflareのキャッシュが全米で作り直されるため、実際より2〜3倍遅い数字が出ます。09-17 15:16 の計測がまさにこれで、スコアが92から56に落ちたように見えました。実際には何も悪くなっていませんでした。
  3. A → B → C の順に、効果が確実な順で並べています。A は効果が読めて副作用がありません。B は検証(効くかどうか試す)です。C は一番効きますが一番慎重さが要ります。
02

手順A — Cloudflare の Tiered Cache を有効にする

5分 · 設定を1つ変えるだけ
A

拠点をまたいでキャッシュを共有させる

1回目の6.03秒を潰す 副作用なし
なぜこれをやるのか。今のモバイルの3回の計測は 6.03s / 2.72s / 2.89s です。1回目だけ突出して遅い。これは Cloudflare が拠点ごとに別々のキャッシュを持っているためで、その都市で最初のアクセスだけ日本のサーバーまで取りに行っています。実ユーザーで言えば「その街で最初の1人」がこれに当たります。Tiered Cache は拠点同士でキャッシュを融通させる仕組みで、これを入れると初めての拠点でも近くの拠点から受け取れます。
  1. Cloudflare にログインします。https://dash.cloudflare.com
  2. サイト一覧から 81drive.com をクリックします。
  3. 左のメニューから Caching をクリックし、その下に出てくる Tiered Cache をクリックします。
  4. 「Tiered Cache Topology」という項目を探します。
  5. 「Generic Global Tiered Topology」を選びます。選択したら自動で保存されます(保存ボタンがある場合は押してください)。
  6. 同じ画面に 「Argo Tiered Cache」という項目もあります。これは有料なので触らないでください。
選べなかった場合
項目がグレーアウトしていたり、「Upgrade」「Pro プランが必要」と出た場合は、その時点でやめて、画面のスクリーンショットを送ってください。無理に有料プランに入る必要はありません。その場合は手順Bに進みます。
終わったら
Purge は不要です。1時間ほど空けてから「計測して」とお声がけください。1回目の数値が6秒台から下がっていれば成功です。
03

手順B — スライダーの自動切り替えを止める(検証)

5分 · 効くかどうか試す作業
B

メインビジュアルが動いているなら止めてみる

効けば最大1秒 元に戻せる
これは「たぶん効く」ではなく「試して確かめる」作業です。LCP は「画面に一番大きく表示された要素が出た時刻」で決まります。メインビジュアルが自動で切り替わる設定だと、計測中に次のスライドへ移った瞬間、その新しい画像がLCPとして記録し直されます。切り替わる前に終われば速く、切り替わってしまえば遅くなる。モバイルの数値が計測ごとに大きく振れているのは、これで説明がつきます。ただし確証はありません。止めて数字が揃えば原因確定、揃わなければ私の推測が外れです。
  1. WordPress管理画面にログインします。
  2. 左メニューの 外観 → カスタマイズ をクリックします。
  3. メニューの中から トップページ をクリックし、続けて メインビジュアル をクリックします。
  4. 「スライド切り替えの間隔(秒)」または「自動再生」という項目を探します。
  5. 間隔の設定なら 0 に、自動再生のオンオフなら オフ にします。
  6. 画面右上の 「公開」ボタンを押します。※ページ下部の「変更を保存」ではありません
  7. Cloudflare → Caching → Configuration → Purge Everything を実行します。
項目が見つからない場合
SWELLのバージョンによって項目名が違います。メインビジュアルの設定画面をスクリーンショットで送ってください。どれを触ればいいか指定します。
どうしても見つからなければ、スライドを1枚だけ残して他を削除しても同じ検証ができます(あとで戻せます)。
判定のしかた
1時間空けて計測します。3回の数値が 2.9秒前後に揃えば、原因はスライダーで確定です。その場合、スライダーを見た目として残したいなら「2枚目以降だけ遅れて読み込む」という別の対処を考えます。
揃わなければ私の推測が外れなので、設定は元に戻して構いません。その時はLighthouseの詳細レポートを開いて、LCPになっている要素そのものを特定します。

手順C — Google Tag Manager を外す

30分 · 一番効くが一番慎重に
C

115KB のJavaScriptを削る

JS 523KB → 約400KB 要事前確認
モバイルを1秒台に入れるには、これしか残っていません。画像は3回の削減でやり切りました(モバイルの画像は合計135KB)。今モバイルの足を引っ張っているのは JavaScript 523KB で、そのうち 115KB が GTM です。そしてGTMは計測上、タグを1つも発火させていません。何も仕事をしていない115KBです。
必ず先に中身を確認してください
「何も発火していない」は私の計測からの判断です。タグが設定されているのに条件が合わず発火していないだけという可能性があります。消す前に必ず手順1〜3で中身を見てください。広告のコンバージョン計測が入っていた場合、消すと計測が止まります。
  1. https://tagmanager.google.com にアクセスし、GTM-WFGD8X5Q のコンテナを開きます。
  2. 左メニューの 「タグ」をクリックします。
  3. ここに何が並んでいるかをスクリーンショットで送ってください。ここで判断が分かれます。
    • 1つもない、または使っていないものだけ → 手順4へ進んで外します
    • Meta Pixel や広告のコンバージョンタグがある → 外さないでください。別の手を考えます
  4. 外観 → カスタマイズ → 高度な設定 → 「headタグ終了直前に出力するコード」を開きます。
  5. 中身を全部コピーして、メモ帳などに保存してください。これが元に戻すための唯一の手段です。必ずやってください。
  6. その中から GTM のコードだけを削除します。<!-- Google Tag Manager --> から <!-- End Google Tag Manager --> までが対象です。先頭に貼った preload の行(rel="preload" で始まる行)は残してください。
  7. 右上の 「公開」を押します。
  8. Cloudflare で Purge Everything を実行します。
外したあと必ず確認すること
GA4(アクセス解析)が止まっていないかを確認してください。GA4 は Site Kit 経由でも入っているので残るはずですが、確認は必要です。
Google Analytics → レポート → リアルタイム を開いた状態で、別のブラウザから 81drive.com にアクセスし、人数が1増えれば正常です。
増えなければ、手順5で保存したコードを貼り戻して「公開」してください。元通りになります。

用語

LCP
画面に一番大きく表示された要素が出るまでの時間。このサイトではメインビジュアルの画像です。Googleの「良い」基準は2.5秒以内。
TTFB
アクセスしてからサーバーが最初の返事をするまでの時間。0.03秒は事実上ゼロです。ここは完全に解決済み。
Purge
Cloudflareが保存している古いコピーを全部捨てる操作。これをしないと、変更してもしばらく古いページが配られ続けます。
拠点(エッジ)
Cloudflareが世界中に置いているサーバー。拠点ごとに別のキャッシュを持つため、その拠点で初めてのアクセスは遅くなります。手順Aはこれへの対処です。
